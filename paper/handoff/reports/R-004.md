## Answer

- **A4 (C18, partial):** each 4 SMs moved from Prefill to Attention raise mean
  TTFT by about 9% and lower ITL by 8–16%. 80/12 vs 84/8: TTFT +8.9%
  [+1.2, +16.8] (point estimate within the 10% criterion, upper CI above it),
  ITL −15.6%, throughput +4.7%, D2 goodput +4.3%; 80/12 is where throughput
  and D2 goodput peak.
- **A2 (C17, supported):** capping the Projection batch below the concurrency
  lowers throughput beyond its CI: cap 16 −1.8% [−2.6, −0.9], cap 8 −33.2%;
  caps 32/64 never bind at C30. Projection step time is strongly sublinear in
  batch size (+17% time for twice the batch).
- **A5/A6 (C19, supported):** migration + Dynamo routing beats Dynamo routing
  alone (TTFT −28%, throughput +13–15%, D2 goodput 2.5× at C50) and sticky
  round-robin (TTFT −4 to −9%, throughput +3–10%); all CIs exclude zero.
- **E5 (G1):** 79–95% of PAP's TTFT — median and tail — is the Prefill phase
  (dispatch to Prefill completion on the PA). Routing, migration, KV
  readiness, Projection admission and the first Decode chunk add < 200 ms.
  PAs are balanced (request-count CV 1–3.5%), so the tail is Prefill
  queueing/compute, not imbalance.

## Deviations from the request

- A2: C30 only (X-003); caps 16/8 added (X-004); the aligned PA/Projection
  trace capture failed (304 aligned steps, tool needs 512), so the step-time
  curve uses the Projection trace alone.
- A5/A6: `sticky-rr` needed the worktree's missing compiled vLLM extensions
  symlinked from the main tree; its first C30 run failed for that reason and
  was rerun.
- E5: the profiling-off control runs at C40 only (2 runs), as requested.
- A4: one run started while unrelated files were staged in git (dirty
  worktree) and was rerun.
- O1–O3: dropped (X-003).

## Validity and limitations

- A2 and E5 CIs are run-level with n = 2 (coarse); A5/A6 n = 3.
- `sticky-rr` is older code; only routing was intended to differ.
- About 7 minutes of idle GPU after the A2 traced run (capture timeout wait).

## Code-change directions (assessed, not implemented)

| Direction | Feasibility | Expected benefit (from these results) |
| --- | --- | --- |
| Dynamic MPS / Green Context split | Medium: per-step SM re-partitioning needs runtime support beyond the static `PAP_STATIC_*` chunks | A4 shows a 4-SM move trades ~9% TTFT for 8–16% ITL; a dynamic split could favour Prefill under TTFT pressure (E5: Prefill phase dominates TTFT) and Attention under ITL pressure. Upper bound ≈ the 84/8 vs 80/12 gap (−8% TTFT) without the ITL penalty at low load. |
| PA-local Projection (no cross-PA aggregation) | Hard: Projection is shared by design; per-PA Projection needs one Projection process per PA GPU or MPS split | A2 already isolates aggregation via the batch cap: losing it costs 2% (cap 16) to 33% (cap 8) at C30. A PA-local variant would cap each PA at ~4 sequences at C30, below cap 8, so expect a large loss. Not needed for the paper. |
| AMPD-style PD baseline | Hard (new PD scheduler) | `sticky-rr` approximates "stay on the KV holder": migration beats it by 4–10% TTFT and 3–10% throughput. |
| Deeper multi-turn (≥ 6 turns) | Easy (dataset only) | PA KV capacity: with native-32K contexts, later turns approach the 32K limit; needs a capacity check before running. |

## Unexpected findings / suggested follow-ups

- To split E5's Prefill phase into queueing and compute, PA-side scheduler
  timestamps (vLLM request arrival vs first scheduled step) would be needed;
  this is a logging change in `vllm/pap` or the PA engine and was not done.
- At C30 the largest Projection batch is 24 sequences; Projection is far from
  saturation, which is consistent with 7PA1P beating 6PA2P everywhere.
