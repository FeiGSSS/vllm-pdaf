## Answer

X0 passed. The PAT split-rank fix has a measurable end-to-end effect: fixed PAT
has 2.9% higher ITL and 2.8% lower throughput than the unfixed kernel, so C10 is
refuted and the G0 gate is triggered. The unfixed kernel also produced wrong
attention outputs where the collision occurred, which the run audits cannot
detect. After the fix, PAT's end-to-end gain over Triton is a 3.6% ITL
reduction only.

## Deviations from the request

- PAT builds are not byte-reproducible (the X0 fixed build hashed `9ef1b544…`,
  the block B build `a136b72b…`). `run.sh` pins the build that was installed
  for each block; a hash identifies an install, not a source revision.
- Throughput/goodput CIs use a run-level bootstrap (one value per run, n = 3),
  latency CIs a request-level bootstrap stratified by run, as in COMMON §2.4.
- X0 PAP TTFT (4.10 s) is slightly below the 4.2–6.2 s sanity band; this is
  faster, not a setup failure.

## Validity and limitations

- 12/12 E0 runs and 2/2 X0 runs valid; no reruns needed.
- The throughput CI for fixed/unfixed only just excludes zero
  (−0.09% upper bound) with n = 3; the ITL effect is the robust one.
- The cause of the fixed kernel's slowdown (fewer shared-CTA splits) is
  inferred from the PR description, not measured.

## Unexpected findings / suggested follow-ups

- **Correctness gap in the run audits.** The correctness audit only checks
  error-log patterns and output lengths, so a kernel that returns wrong
  attention values passes it. Suggest a token-level output check (e.g. a
  greedy, fixed-seed reference against Triton on a few requests) before the
  paper's headline runs. This needs a change in `benchmarks/pap/scripts/`, so
  I am only proposing it.
- PAP ITL today (fixed PAT 48.0 ms) is 6% above September's 45.2 ms: about
  3% from the fix and the rest consistent with the 6–8% day-to-day slowdown
  already noted in COMMON §1.
