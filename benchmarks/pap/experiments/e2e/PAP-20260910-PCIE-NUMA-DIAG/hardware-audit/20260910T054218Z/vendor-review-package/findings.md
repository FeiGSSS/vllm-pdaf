# Hardware fault evidence recovered from persistent panic storage

Six distinct ERST/pstore panic archives are present in systemd journal FILE attachments. Normal kernel journal missed the terminal error. The root-owned/nobody-owned raw archive files were not readable, but systemd-pstore's journal attachments are readable by this user; journalctl --all is essential because otherwise large FILE fields appear null. No permissions changed or bypassed. Raw journal export and decoded original fragments preserved here. recover-pstore.py was validated against all six archives.

All six have: APEI/GHES fatal PCIe hardware error; affected endpoint is NVIDIA10de:26ba; aer_uncor_status0x00014000, mask0, severity0x00476030; terminal `Kernel panic - not syncing: GHES: Fatal hardware error`. Endpoints in chronological archive order: f1,f1,e1,e1,f1,71. This matches changing GPU7/GPU6/GPU3 BMC locations.

Decoded using /usr/include/linux/pci_regs.h:0x00004000=Completion Timeout;0x00010000=Unexpected Completion. Both status bits are unmasked and fatal in the recorded severity. Correctable status0x00008000=Header Log Overflow. No Malformed TLP(0x40000), Unsupported Request(0x100000), or ACS Violation(0x200000) bit is set in this uncorrectable status. All-zero TLP headers prevent identifying the original transaction/tag/address here. Do not read First Error Pointer00 as a valid cause without a valid captured header.

Direct mechanism now established: fatal PCIe completion-response anomaly reported at GPU endpoint -> firmware APEI/GHES NMI handler -> kernel panic. It is not merely an application request deadlock or unexplained whole-host stall. The underlying cause of the completion anomaly (device/firmware/driver/platform routing/electrical issue) remains unproven. Timeout plus unexpected completion could be related, but no ordering evidence proves a late completion mechanism or identifies NIC as the counterpart. MPS mismatch does not follow from these error bits, so it is not established as the cause.

Current read-only health observations: all8 GPUs same VBIOS95.02.7C.00.06, aggregate corrected and uncorrected ECC totals0; EDAC mc0/mc1 CE/UE0; mlx5 devlink fw/fw_fatal/vnic healthy,error0,recover0 after reboot. These do not rule out the earlier PCIe fault. CPU is dual AMD EPYC9575F, microcode0xb002161; BIOS01.07.00 dated2025-10-16; NVIDIA open kernel driver595.84; kernel7.0.0-31. No stress workload, hardware reset, register write, BIOS change or driver installation performed in this audit.

Correction to previous reports: statements that no fatal subtype/panic record was available were incomplete because pstore had not been examined. Persistent panic records have now supplied the subtype and direct machine-stop mechanism. Previous kernel-journal negative findings remain true only for that data source. Root cause is NOT a proven defective NIC or GPU. No new postmortem upload attempted.
